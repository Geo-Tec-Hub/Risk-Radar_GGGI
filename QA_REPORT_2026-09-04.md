# QA report — Risk Radar, Central Province slice

**Date:** 2026-09-04 · **Scope:** `QA_BRIEF.md`, Central Province · **Method:** live reproduction against a running API (:8000), Angular (:4200) and `riskradar` database — no fixes applied.

## Before you read the findings: the environment did not start in the documented state

The brief says to confirm the baseline before testing "because every later test is meaningless against a different dataset." At the start of this session it did not match:

- `GET /api/health` returned `{"status":"degraded","database":"unavailable"}`. Postgres was running and port 5432 was reachable, but the uvicorn process had no DB credentials in its environment (no `$env:PGPASSWORD`, no working `pgpass.conf` — matches the existing memory note that the pgpass route doesn't work on this machine). Restarting the API with `PGPASSWORD` set fixed this (with the user's permission and password).
- Once the API could reach the database, `indicator_value`, `vulnerability_result`, `import_batch` and `computation_job` were all **0 rows** — not the brief's 4,412 / 1,323. Central's data had never been loaded into this database instance.
- Loading it via `RUN_LOCALLY.md §3`'s documented sequence (`panel_central.sql` → `seed_central.py` → `compute_all.py`) failed on step 2 with `UndefinedColumnError: column "value_kind" does not exist` — see **Finding 4** below.

After applying the missing addendum and running the documented load sequence (all with explicit user approval), the baseline matched exactly and the QA pass proceeded:

```
340 DS divisions, 340 surveyed, 0 boundary-pending, 66,037 km²        ✓
33 active Central profiles, all is_computable (33/33)                 ✓
4,412 indicator_value rows, period 2021-2025                          ✓
1,323 vulnerability_result rows                                       ✓
```

This is reported as **Finding 3** below because it means the documented "app is running" / "run these three commands" path does not currently produce a working, data-loaded environment unattended.

## What passed (confirmed, not just read)

- **Registration/approval/sessions (brief §1):** pending → active/rejected transitions correct; non-admin and unauthenticated `POST /admin/registrations/{id}/approve` both fail closed (403/401); `app_user_approval_recorded` CHECK constraint holds under a direct SQL attempt to violate it; reused session cookie after logout → 401; **FR-5.21** confirmed — revoking a session server-side while the browser holds the stale cookie, the header correctly flips from "Sign out" to "Sign in"/"Register" the moment a protected action is attempted (401 received).
- **Import pipeline (brief §2):** Check/Import agree exactly (328 read / 328 loaded, 41 divisions, both runs); Paddy file under Livestock/Cattle refused, naming both scopes, nothing loaded; a two-error corrupted file (negative value in a non-signed variable + text in a numeric cell) returned **both** errors together, `batchId: null`, row count unchanged; re-importing the same file as a second (admin) account left the row count at 4,412 with the brief's duplicate-check query returning `0` — the 3 Sep fix holds; unauthenticated check/load both 401; oversized (22 MB) file correctly 413.
- **Weights business logic (brief §3, tested directly against the API since the editor UI is broken — Findings 1–2):** exposure domain forced to 101% → `422` naming domain and total; marking a variable `contested` with no note → `422` naming the variable; excluding (`rejected`) a variable persisted with `decided_by`/`decided_at` set (the 15 Aug regression stays fixed); each save created a genuinely new profile version and retired the previous one (confirmed twice, V2→V3→V4).
- **Computation engine (brief §4):** two consecutive `compute_all.py` runs produced byte-identical result sets (0 differing rows, comparing `vulnerability_index`/`hazard_index`/`exposure_index`/`bound_min`/`bound_max`); every active profile has exactly one division at 1.000; the 4 refusal/positive-control behaviors all correct when verified directly (see Finding 6).
- **Map and API (brief §5):** Cattle Farming/Drought's NU5/NU6/NU7 render `state: unassessed`, `value: null`, `band: null`; Inland Fishery/Drought's 19 of 41 divisions render `state: not_applicable`, `value: null`/`band: null` with `zeroIsStructural: true`, flat on the map, unselectable (click produces no panel), and counted separately in the coverage statement ("22 assessed (54%) ... 19 where the sector is not present (46%) — 41 DS divisions"); coverage denominator is Central's 41 divisions everywhere, never the national 340; `indexScope=national` → `409` with a clear reason; switching province (Central → Southern) correctly re-fits the map view to the new province and no longer renders Central; a division's API figures (`value`, `hazardIndex`, `exposureIndex`) matched the raw `vulnerability_result` row exactly.
- **Cross-cutting (brief §6):** no SQL-injection-style probe leaked a raw database error or executed as SQL (parameterized queries throughout); the only crash found (Finding 7) leaks a generic message, not a stack trace, to the client.

## What I could not test

- **"Stop the API, confirm the map says so."** Tried three ways to reproduce a genuine backend outage from the browser's perspective: (1) killing the uvicorn process left a "ghost" listening socket that kept serving 200s under a PID `Get-Process`/`taskkill` could no longer find — a sandboxing artifact of this session, not the app; (2) a temporary firewall rule was correctly refused by the safety classifier as a system-security-setting change; (3) stopping the PostgreSQL Windows service failed with insufficient permissions even after explicit user approval. Fell back to code inspection: `frontend-angular/src/app/core/interceptors/api-error.interceptor.ts` explicitly maps a network-unreachable response (`status === 0`) to `"Could not reach the server."` for every request through one global interceptor, and the same per-component error-surfacing pattern (`this.error.set(err.message)`) was confirmed live for a different failure mode (a 404 "no active profile" case) in Finding 5's reproduction. Reasonable confidence, not a live confirmation.
- **Detail-panel click-through for an assessed (colored) division.** Clicking directly on visually-confirmed, in-bounds canvas coordinates for both hatched and colored divisions never opened a score-composition panel in this session. Since clicks on hatched/not-applicable divisions are *supposed* to do nothing (confirmed correct), and the assessed-division clicks behaved identically, I can't be confident this is a real defect versus a synthetic-click/OpenLayers canvas hit-testing limitation of the browser automation tool itself — screenshots and console showed no errors, and basic DOM clicks (buttons, dropdowns, nav links) worked reliably throughout the session. I instead confirmed the underlying figures directly: a division's `/api/vulnerability` values matched its raw `vulnerability_result` database row exactly (see passed items). Not reporting this as a finding per the brief's "reproduction, not looks-wrong" standard — flagging it as an honest gap instead.
- **`/coverage` page and `/entry` (data-entry track)** — not in the brief's checklist; not exercised.
- **Expert and community tracks** — the brief's import/value checks all target the `data` track; `expert`/`community` were not separately exercised.
- **Provinces other than Central** — confirmed the other 8 correctly report "no active profile" (expected: no data loaded for them), but did not sweep them as thoroughly as Central since they carry no data in this database.
