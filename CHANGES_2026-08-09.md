## C1 — Normalisation is provincial, and a province holds until complete

**Before.** Bounds computed across all 330 divisions nationally `[P-2]`. Fixed ceilings
preferred over holding `[P-3]`; 134 count/extent variables needed a stated maximum.

**After.** A variable is min–max scaled across the divisions of **one province**, computed
only once **every division of that province holds a value**. A province publishes without
waiting for the other eight. No ceilings needed.

**Why.** Data arrives in instalments as workbooks are updated, so "hold until all 330
report" would mean nothing publishes for months. Provincial hold gives stability — once a
province is complete its bounds never move — without requiring 134 judgements.

**Cost, accepted knowingly.** A normalised indicator value is **no longer comparable
across a provincial boundary**. The relativisation now happens twice: once per variable,
once on the index.

**Spec.** §2.2, §2.1 scope table, FR-4.3, FR-4.5, FR-4.5b, Annex C `[P-2]` `[P-3]`.

### Change in code

- **Engine (to build).** Bounds query is scoped to the province and gated on that
  province's completeness. A province that is not complete returns **no scores at all**,
  not partial ones.
- **`core/models/vulnerability.model.ts`** — `VariableContribution.normalisedValue` is now
  province-relative. Document it on the interface, because every consumer of that field
  now needs a qualifier.
- **`features/map/division-panel.component.html`** — the composition panel must say
  *"normalised within X Province"* beside indicator values, not present them bare
  (FR-5.9).
- **Anywhere offering cross-province comparison of an indicator** — remove it. There is no
  longer a common scale.
- **Do not** implement `norm_scope = fixed_bounds` as the default path. It remains valid
  only for the 36 percentage variables and 4 fixed-scale indices.

**Verify.** Entering 24 of 25 divisions in a province yields zero published scores for it,
not 24.

## C2 — Two indexes, coexisting

**Before.** One index per division. An intermediate formulation had the national index
*replacing* the provincial one, with every published score restated once.

**After.** A division carries **two** vulnerability indexes for the same profile and
period:

| | Provincial | National |
|---|---|---|
| Bounds | Its own province | All divisions nationally |
| Exists when | That province is complete | **Every** division in the register is |
| Status | **Headline published score** `[P-14]` | Comparison view, labelled |

Neither overwrites the other. **Nothing is ever recomputed or restated.**

**Spec.** §2.2 "Two indexes, not two phases", FR-4.3b, FR-4.3c, FR-5.24b.

### Change in code

- **`vulnerability_result`** — `index_scope` ENUM `('provincial','national')` is now part
  of the unique key, with `bound_min` / `bound_max`. Already in
  `schema_consensus_addendum.sql`; not yet applied.
- **`core/models/vulnerability.model.ts`**
  - add `indexScope: 'provincial' | 'national'` to `VulnerabilityUnit`
  - add `indexScope?` to `VulnerabilityQuery`
  - **rename `VulnerabilityComposition.provinceMin` / `provinceMax` → `boundMin` /
    `boundMax`.** The current names are wrong under the two-index model: for a national
    index the bounds are not provincial. This is a real defect, not cosmetic.
- **`core/services/api-client.service.ts`** — pass the scope on `/vulnerability`,
  `/vulnerability/{unit}` and `/coverage`.
- **`features/map/filter-bar.component.html`** — add a scope control. It must be disabled,
  with a reason shown, while the national index does not exist (which is now, see C8).
- **`features/map/coverage-legend.component.*` and `coverage-style.ts`** — the legend must
  name the scope. **Never render both scopes under one legend.**
- **Exports** — carry the scope as a column, not a footnote.

**Verify.** Two rows differing only by `index_scope` insert successfully. An export names
its scope. Switching scope in the UI never mutates a stored value.

## C4 — An unweighted variable is excluded, not weighted

**Before.** `[P-6]`: equal weight applied across the exposure domain as an interim,
replaced profile by profile. The engine refused to compute any profile containing an
unweighted variable (FR-4.9).

**After.** A blank weight means the variable is **not significant**, so it is excluded and
the remaining weights must total **exactly 100**. If they do not: **warn and refuse to
compute.** Never rescale the entered weights to reach 100.

**Critically: exclusion is a recorded decision, never an inference.** The system must not
read a blank as "not significant" on its own — it asks on save and stores the answer
(`consensus='rejected'`) with the user and date. A blank cannot otherwise be told apart
from an oversight.

**Measured effect.** 213 of 243 exposure groups already total 100 once blanks are
excluded; **30 warn**. Combined with C5, **97 of 243 profiles compute immediately** —
Central 29, Western 24, Southern 22, Sabaragamuwa 22.

**Spec.** §2.4, FR-4.9, Annex C `[P-6]`.

### Change in code

- **`v_profile_readiness`** — already redefined in the addendum: counts only `agreed` +
  `contested`, so a `rejected` variable neither carries weight nor blocks.
- **`core/models/profile.model.ts`**
  - `ProfileVariable.weightPct: number | null` — the doc comment says *"null means belongs
    to the profile, weight not set yet"*. Still true, but now add: **resolved by exclusion,
    not by supplying a weight.**
  - add `consensus`, `consensusNote`, `decidedBy`, `decidedAt`
  - `SaveWeightsPayload` must carry consensus changes, so one save handles both
- **Weights API** — reject a save whose domain reaches 100 only by counting a `rejected`
  variable.
- **Do not implement equal-weight fallback anywhere.** `[P-6]` is superseded; equal weight
  would silently alter every other weight in the domain.

**Verify.** A profile with blanks and a 100 remainder computes. One with an 85 remainder
warns and produces no score.

## C5 — The hazard exception to C4

**Before.** N/A — C4 is new.

**After.** In the hazard domain, exclusion is permitted **only where the blank is a
composite hazard index**. Where a *component* is blank while the composite carries the
weight, the profile **holds**.

**Why this exists.** Applying C4 mechanically to the hazard domain hands the entire domain
back to the composite index, silently reversing `[P-5]` and making scores
non-decomposable. Measured against `seed_all.sql`:

| Hazard-domain shape | Profiles | Outcome |
|---|---|---|
| Components weighted, composite blank | **115** | Exclude the composite — this *is* `[P-5]`. Computes |
| Composite weighted at 100, components blank | **128** | **Hold**, pending components |

Without this rule, **0 of 243** profiles compute — every hazard group contains a blank.

**Spec.** FR-4.9b, §2.4.

### Change in code

- **Engine and weights API** — key on *what* is blank, not on which domain it is in.
- **`features/weights/weights-editor.component.ts`** — offer the exclusion prompt in the
  hazard domain **only** where the blank is a composite index. Where a component is blank
  and the composite carries weight, state that the profile is held pending data and do not
  offer exclusion at all.

## C6 — The accepted set is declared by the data-entering user

**Before.** A draft of the addendum carried `dissent_count SMALLINT` — how many panel
members objected to a variable.

**After.** Removed. The declaration of which variables are accepted is made by **the user
entering the data**, captured by `decided_by` + `decided_at`. Disagreement worth keeping
goes in `consensus_note` as prose.

**Why.** Counting objections assumes a meeting procedure that does not exist, and a count
nobody actually records is worse than none — it looks like evidence.

**Second half of the same decision:** an expert who adds a variable must be given a route
to that variable's **data** in the same flow (FR-1.4b). Under C1, a variable added without
values **holds the entire profile indefinitely**.

**Spec.** §2.4, FR-1.4, FR-1.4b, FR-1.4c.

### Change in code

- **`schema_consensus_addendum.sql`** — `dissent_count` already removed. It was never
  applied, so there is no migration.
- **Profile composer / weights editor** — adding a variable must offer template download or
  manual entry immediately, and state how many divisions need a value.
- **Adding or removing a variable creates a new profile version** and must show the forced
  re-weighting before saving: 401 of 486 domain groups already total exactly 100, so an
  addition pushes the others down.

## C7 — Exploratory workspace is experts only

**Before.** Undecided who could use it.

**After.** **Expert and Administrator roles only.** No public access, no community
contributors, no data officers.

**Why.** Open access produces aggregates that look like public opinion but measure only
whoever used the tool. Public perception has its own instrument — the **community track**,
structured and per division. The two must never be conflated.

**Practical benefit:** no rate limiting and no public-facing disclaimer needed.

**Spec.** §3, §3.2.

### Change in code

- **`vulnerability_profile.publication`** — `published / draft / sandbox`, with
  `owner_user_id` required for anything not published, and one published+active version per
  scope. In the addendum.
- **Angular route guard** on the exploratory routes.
- **Read through `v_official_profile`**, not by filtering `vulnerability_profile` at each
  call site — so a draft cannot reach a public surface by omission.
- **Containment stands regardless of who has access:** nothing persisted, watermarked
  exports, no tiles, no OGC. The trigger `vulnerability_result_no_sandbox` enforces the
  first at the database.

## C10 — Landing page, sign-in and self-registration

**Before.** The Angular app opens straight onto the map. There is **no landing page, no
login screen and no authentication anywhere in the client** — `ApiClientService` has no
auth calls at all. `app.routes.ts` maps `path: ''` directly to `MapPageComponent`.

**After.** A landing page is the entry point, offering two routes:

1. **View the map** — no account, straight through. **This must stay one click away**;
   §3.1 and FR-5.1 depend on it. The landing page is a front door, not a gate.
2. **Sign in / register.**

Registration is self-service and the registrant picks one of three types:

| Chosen at registration | Role granted | May then |
|---|---|---|
| **Data entry authorised agency** | `data_officer` | Enter indicator values, one assigned province |
| **Expert** | `expert` | The above, plus expert values, accepted-set declaration, exploratory workspace |
| **Public user** | `community` | Submit a 1–5 severity rating. **Not** indicator values |

**No account writes anything until an administrator approves it.** Accounts are created
`pending`. Approval grants the role and — for agency and expert — assigns the province.

**"Authorised agency" is a role held by a person, not an organisation.** No organisation
table. Accept the consequence: the system cannot reliably answer *"which agency supplied
this figure?"*, and one officer's work cannot be reassigned when they leave. Adding an
organisation entity later is additive.

**Spec.** §3, §3.5, FR-12.2, FR-12.7 to FR-12.10.

### Change in code

- **`schema_auth_addendum.sql`** (new): `account_status` ENUM
  `pending / active / rejected / suspended` on `app_user`, plus `requested_role_id`,
  `province_id`, `approved_by`, `approved_at`, `rejected_reason`, `registered_at`.
  `v_pending_registration` and `v_user_access` for the admin dashboard.
- **`is_active` defaulted to TRUE** in `schema.sql` — exactly wrong for self-registration,
  since an account could write the moment it was created. `status` is now the authority
  and defaults to `pending`; a trigger keeps `is_active` in step so existing reads survive.
- **Role rename.** `schema.sql` seeds `analyst`; the SRS role model has never had an
  Analyst — it has a **Data officer**. The seed was wrong. Renamed to `data_officer`,
  display name "Data Entry Agency". **Do not reintroduce `analyst`.**
- **Angular** — new routes: `/` becomes the landing page, map moves to `/map`, plus
  `/login`, `/register`, `/admin/registrations`. Add an auth guard, a session service, and
  auth calls on `ApiClientService`. FR-5.21 already requires the client's session state to
  match the server's — do not let it appear signed in while the API rejects it.
- **Hiding an action in the UI is never the only control** (FR-12.8). Every write is
  authorised server-side against role and province.

**Verify.** A pending account can read everything public and write nothing, and is told
which state it is in rather than failing silently.

## C11 — Provincial scope became enforceable

**Before.** §3.2 has always said a data officer or expert is bound to one province, and
that the bound is enforced server-side on every write. **The schema had no support for
it.** `app_user` carried no province and `user_role` is only `(user_id, role_id)`. The
rule was specified, printed in the roles table, and impossible to enforce.

**After.** `app_user.province_id`, plus a trigger on `user_role`:

- granting `data_officer` or `expert` to a user with no province **fails**
- granting `admin` to a user who *has* a province **fails** — administrators are national

A trigger rather than a CHECK because the rule spans two tables.

**Spec.** §3.2, FR-12.9.

### Change in code

- Every write path must filter by the authenticated user's province — imports, manual
  entry, weight saves, toolbox commits.
- The province selector in `features/entry/profile-context.component.html` and
  `features/map/filter-bar.component.html` should be **pre-set and locked** for a data
  officer, not a free choice. Reading nationally stays open.

**Verify.** A Central officer uploading an Eastern workbook is rejected server-side, with
V004 (`division outside the officer's province`) — the validation code already exists.

## What did **not** change

Check against this before editing; it is easy to over-correct.

- The formula. `V_raw = Hazard × Exposure`, still the raw product `[P-1]`.
- The provincial **index** rescale `[P-14]` — unchanged, still the headline. Whether it
  still earns its place is open item `[O-11]`, to be answered from real values at Stage 4,
  **not from theory**. The formula has changed three times in eight days.
- Three coverage states: assessed / pending / unassessed. Pending is not zero.
- No approval workflow in V1. Panel review is offline, recorded in `panel_note`.
- Weight saves are versioned, never in-place.
- 174 variables · 33 national profiles · **243** province-profiles · 3,664 memberships ·
  1,783 NULL weights.
- Year ranges, latest period wins. Geometry 4326, measurement 5235.
- The stack: Angular + TypeScript · OpenLayers · FastAPI · PostgreSQL + PostGIS + pgvector.
